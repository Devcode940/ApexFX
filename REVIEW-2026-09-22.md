## 1. Executive decision

**ApexFX is a substantial prototype with a useful technical foundation, but I would not approve it as a trustworthy paper-trading/analytics product yet.** It has no broker execution integration; the concerns here are incorrect simulated results, loss or mixing of user records, misleading market state, and exposure of the operator's paid API budget—not evidence of real-money orders being placed.

The most consequential problems are not formatting, file size, or missing frameworks:

1. **JPY/CAD P&L is added to USD P&L and displayed as dollars.** A one-lot USD/JPY move from 150 to 151 produces `100000`, displayed as dollars although it is JPY; at the exit conversion rate it is about **USD 662.25**.
2. **A stop touched between throttled updates can be missed.** I reproduced `1.10 → 1.08 → 1.10` with a BUY stop at `1.09`: the position remained open.
3. **Chart history can remain empty indefinitely**, including on the initial development mount under the repository's own StrictMode wrapper.
4. **The chart never creates a new candle from ticks**, and the incremental chart path updates candles but not their indicator series.
5. **Cloud sync can lose, resurrect, or misattribute records.** A position opened during a pull was discarded; a closed position's old remote row can return; retained account-A data can be uploaded as account B.
6. **Production WebSocket token acquisition rejects the browser's ordinary request.** Polling can still work, but streaming does not work as advertised under the default production token flow.

Existing tests all pass. That is useful evidence about the implemented helper contracts, **not evidence that these user workflows are correct**.

### Priority convention

- **P1 — release blocker for the affected feature:** incorrect calculations, lost/mixed records, broken normal workflow, or material paid-service exposure when publicly enabled.
- **P2 — next hardening work:** resilience, scaling, operational correctness, misleading analytics, and maintenance.
- **P3 — polish:** lower-impact interaction and presentation work.

No verified critical remote compromise is claimed. Conditional risks are explicitly marked; a local reproduction with a mocked provider is not a successful test against that provider.

## 3. Architecture: keep the foundation, repair the contracts

Current flow:

```text
Twelve Data / Yahoo / Frankfurter
        ↓
Express services → mutable process-local watchlist + caches
        ↓                         ↓
WebSocket messages             HTTP polling/history
        └───────────┬─────────────┘
             useWatchlistFeed
                    ↓
              TradingContext
          ┌─────────┼──────────────┐
      chart data  signals     paper-trading state
          ↓                       ↓
   chart primitives       global localStorage keys
                                  ↕
                      manual Supabase push/pull
```

### What is genuinely good

- React/Vite/Express is a reasonable stack for this product. A framework rewrite is not necessary.
- Trading calculations, rate-limit policy, symbol mapping, and candle aggregation have been extracted into testable modules.
- `computePnl` clearly documents its quote-currency output. The failure is its integration with dollar-denominated consumers, not a mysterious multiplication error.
- Epoch-based 4H aggregation is better than grouping every four array entries; existing tests cover gaps and ordering.
- Explicit price-zero/order-size guards, UUID-based IDs, and removal of setters nested inside state updaters are meaningful improvements.
- RLS policies and per-user composite primary keys are appropriate database controls. The account-mixing issue below is a client ownership problem, **not evidence that RLS is bypassed**.
- ESLint, strict TypeScript, and test failures are no longer swallowed in the main build job.
- The logger redacts multiple arguments, CORS is not a credentialed wildcard in production, and the simple query parser reduces the exposed `qs` query-parsing surface.
- Client-to-server requests use relative URLs. The production server binds to `0.0.0.0`.

The missing architectural center is an explicit model for **quote identity/freshness, money currency, order lifecycle, and account ownership**. Hooks and components currently have to guess those facts.

## 4. Findings and concrete fixes

### R1 · P1 — Portfolio P&L mixes currencies

**Evidence:** `src/utils/paperTrading.ts:31–40,131–150,179–190`; `src/components/PerformanceDashboard.tsx:106–167,318–329`; `src/components/PositionsPanel.tsx:276–294`.

`computePnl` returns `(exit − entry) × lots × contractSize`, with direction applied. That is quote-currency P&L. Both dashboards aggregate `pnl` directly and display dollars. The `pipValueUsd` risk-calculator helper does not convert the trade ledger.

**Reproduced:**

```text
BUY USDJPY, 1 lot, entry 150, exit 151
computePnl → 100000 JPY
USD equivalent at USDJPY=151 → 662.25 USD
Add an EURUSD trade with +1000 USD:
current aggregate → 101000, rather than approximately 1662.25 USD
```

This contaminates equity curves, average wins/losses, cross-instrument profit factor, CSV exports, and persisted `profit` values.

**Recommendation:** define account currency and retain `pnlQuote`, `quoteCurrency`, `pnlAccount`, and the conversion rate/source/time. Use the symbol's own exit rate for USD-base pairs; a GBP/JPY trade needs a USD/JPY conversion quote. Freeze the conversion basis on closing rather than revaluing historical realized results using today's rate. Represent missing conversion explicitly, not by returning a quote amount from a function named `pipValueUsd`.

**Required test:** a mixed EURUSD/USDJPY/USDCAD/GBPJPY portfolio, long and short, missing conversion quotes, and closed-trade restoration. Version existing stored rows; do not silently reinterpret old JPY/CAD amounts as USD.

### R2 · P1 — The execution throttle can erase a stop/target touch

**Evidence:** `src/hooks/usePaperTrading.ts:109–130`; `src/utils/paperTrading.ts:109–156`; `src/utils/throttle.ts:32–66`.

A 500 ms throttle invokes the entire mark-to-market/exit engine against the **latest** watchlist ref. Keeping the last tick is sufficient for repainting a P&L label, but not for determining whether a barrier was crossed during the interval.

**Reproduced with the real hook:** initial EURUSD `1.10`, BUY SL `1.09`, then `1.08`, then `1.10` inside the window. After the trailing run: **one open position, zero closed trades**.

**Recommendation:** process ordered quote events for execution; throttle only visual state publication. If batching, preserve the relevant path/extrema and ordering—an interval that touches both SL and TP cannot be resolved accurately from the final price alone. Make closing idempotent against an original position ID.

Also distinguish the current **idealized fill model** from broker execution: `markToMarket` always fills exactly at SL/TP even after a gap and charges no spread, slippage, or fees. That can be an explicit simulator policy, but not an unqualified “broker-accurate” claim. Normal stop orders can execute away from their trigger price; the investor explanation illustrates this distinction. [1](https://www.investor.gov/introduction-investing/investing-basics/glossary/stop-order)

**Required test:** touch/rebound, gap, multiple observed crossings, BUY/SELL mirrors, duplicate quote event, and reload/reconnect. Clearly state that this client-side engine does not keep executing while the application is closed.

### R3 · P1 — History cancellation permanently poisons a cache key

**Evidence:** `src/hooks/useChartHistory.ts:10,19–28,65–72`; `src/main.tsx:8–13`.

The hook marks a key loaded **before** the request succeeds. Cleanup sets the request's `active` flag false, but never clears the key. A replay or revisit skips the request even though no usable data was installed.

**Reproduced:**

| Scenario | Fetch count | Final candles |
|---|---:|---:|
| Normal non-StrictMode control | 1 | 1 |
| Initial StrictMode mount/replay | 1 | **0** |
| EURUSD → GBPUSD → EURUSD before responses finish | 2 total | **0 for EURUSD** |

A failed response is also never retried for that key. “Initializing Forex charting buffer…” can become a permanent state. React explicitly documents the development effect replay; the repository enables it. See [React StrictMode documentation](https://react.dev/reference/react/StrictMode).

**Recommendation:** track `idle/loading/success/error` per key, commit “loaded” only on success, allow retries, cancel or supersede old requests safely, and expose loading/error/retry in the UI. Use a small well-defined query cache or an existing query library. Do not fix this by disabling StrictMode or suppressing dependency rules.

**Required test:** StrictMode, A→B→A with deferred responses, failed-then-successful retry, stale response arrival, and unmount.

### R4 · P1 — Candle and indicator lifecycles diverge

**Evidence:** `src/context/TradingContext.tsx:173–201`; `src/hooks/useChartHistory.ts:19–72`; `src/hooks/useChartCore.ts:219–270,522–567`.

There are three related integration defects:

1. Every live price overwrites the final historical candle's close/high/low. There is no timeframe-bucket comparison, new-bar creation, or subsequent history reconciliation. The bar timestamp remains unchanged indefinitely.
2. The incremental chart effect updates only `candleSeries`. SMA, EMA, Bollinger, Fibonacci, RSI, MACD and captured crosshair RSI values remain based on the data used when the chart was created. Signals elsewhere can therefore disagree with the displayed overlays.
3. `data.length` is a chart-construction dependency. Once rollover is implemented, appending a bar currently recreates the chart and resets its visible range instead of simply extending its series.

**Reproduced:** a fixture candle kept its old timestamp and array length after a later live price changed its close. In a chart-adapter test, an intra-bar tick caused **one candle update and zero overlay updates**; appending one bar recreated the main chart.

A further leak is present in the same file: `createSeriesMarkers` is called on initialization and each marker update, and the returned plugin is discarded. It attaches a new primitive rather than updating the old one. Ten calls attached ten primitives in a controlled API probe. Use the returned object's `setMarkers` and `detach` methods, as the library documents. [5](https://tradingview.github.io/lightweight-charts/docs/api/functions/createSeriesMarkers)

**Recommendation:** introduce timestamped quote events and a tested bar reducer; reconcile missing intervals from authoritative history rather than fabricating complete OHLC bars from sparse prices. Separate chart construction, data updates, and overlays. Keep one marker plugin per series. Define a shared data revision for indicators and the chart.

**Required test:** intra-bar update, new bucket with unchanged price, several missed buckets, market reopen, corrected history, indicator parity, constant marker-plugin count, and preservation of zoom across new bars.

### R5 · P1 — “Live”/“healthy” does not establish fresh or executable data

**Evidence:** `server/services/market.ts:139–198,228–230`; `server.ts:284–302,372–383,532–563,582–605`; `src/hooks/useWatchlistFeed.ts:37–51,145–154,217–231`; `src/context/TradingContext.tsx:166–171`; `src/components/PositionsPanel.tsx:142–145`.

- Quotes have no per-instrument upstream timestamp, freshness state, or instrument kind.
- HTTP/WS payload timestamps are generated when sending, even if the underlying price is old.
- `/api/health` says `ok` once **any** stored price is positive; it does not expire that state.
- The client declares `live` on socket open, before checking authenticated/usable/fresh market data.
- The initial Frankfurter request unconditionally overwrites nonzero feed prices when it eventually completes.
- `currentPrice` can fall back to a historical close, and the order ticket treats any positive price as a live executable price.
- Yahoo non-2xx responses skip the body but do **not** count as failures. Consequently HTTP 429/503 does not advance the backoff streak.

**Reproduced:** eight Yahoo 503s produced `{attempted:8, applied:0, failed:0}`, failure streak `0`; a delayed daily snapshot replaced a streamed `1.20` with `1.10`; setting one cached positive quote made health `ok` without any age evidence.

Frankfurter's latest endpoint is a **daily working-day reference rate**, not a real-time FX tick feed. Its own documentation says it updates around 16:00 CET. The server's label `Frankfurter Real-time API` is inaccurate. [3](https://frankfurter.dev/v1/)

**Recommendation:** carry `provider`, `providerSymbol`, `instrumentKind`, `asOf`, `receivedAt`, and `quality` per quote. Differentiate transport state from data quality. Reject or explicitly label stale/reference-only execution. Only seed missing prices with the daily snapshot, and never let it overwrite a newer feed quote. Count non-2xx, invalid payloads and zero-applied cycles as degraded outcomes.

**Required test:** old quote after a fresh quote, partial-symbol outage, all-symbol outage after earlier success, slow daily bootstrap, 429/503 backoff, and execution with only historical/reference data available.

### R6 · P1 — Additive cloud merge is not a safe trade lifecycle

**Evidence:** `src/components/SupabaseSync.tsx:139–184,196–254`; `src/utils/supabaseSync.ts:17–41`; `src/utils/paperTrading.ts:141–156,180–196`.

Two separate failures are present:

**A. Lost local changes during a pull.** `handlePullSync` captures `positions`/`closedTrades`, awaits two requests, merges against those captured arrays, then replaces current state. The helper preserves the snapshot it was given, not records created after that snapshot.

**Reproduced with the component:** started a pull with one position, opened another while the response was pending, completed an empty remote response. The second position disappeared.

**B. Closed positions can return.** Push upserts current positions and trades but does not delete/close old remote positions. Close creates a new trade ID with no original `positionId`. Pull takes the union, so the old open position can be resurrected beside its closed-trade record. “Clear history” is likewise not a cloud deletion protocol.

**Recommendation:** apply pull results to the latest state through a reducer/functional updates, and represent lifecycle explicitly. A versioned position record with status/closed time, or a small idempotent event ledger, is sufficient; a full distributed-event platform is not required. Use a stable original-position link, revisions/tombstones, and atomic database transitions where cloud sync is authoritative. Don't solve deletion by blindly deleting all rows absent from one device.

**Required test:** open→push→close→push→pull; open/close while a pull is in flight; retry a close; two devices with conflicting revisions; clear/restore; and partial failure between the two table writes.

### R7 · P1 — Local trade data is not scoped to an account

**Evidence:** `src/hooks/usePaperTrading.ts:44–95`; `src/components/SupabaseSync.tsx:62–73,113–127,140–148,165–168`.

`forexinsight_positions` and `forexinsight_closed_trades` are origin-global keys. Signing out changes the Supabase session, not the trading book. The next signed-in user's push attaches their `user_id` to whatever remains in that book.

**Reproduced with mocked authentication:** retain `account-A-position`, log out, sign in as B, press Sync. The upload contains `id: account-A-position, user_id: account-B`.

This can expose A's records on a shared browser and copy them into B's account. **RLS is doing what it was asked to do**—inserting a row owned by B—so adding another `.eq('user_id', ...)` alone does not solve it.

**Recommendation:** namespace local state by account, keep a separate guest book, explicitly opt into guest-data import, switch/clear in-memory state on auth changes, and invalidate in-flight sync operations when the session changes. Decide the intended shared-device privacy model and document it.

**Required test:** A→logout→B; reload while signed out; guest→account import; pending account-A pull completing after login as B.

### R8 · P1 — Switching cached symbols can overwrite saved drawings

**Evidence:** `src/components/TradingChart.tsx:82,230–233`; `src/utils/chart/drawingTools.ts:14–35`; `src/App.tsx:346–359`.

Drawings are loaded only in the state initializer. The persistence effect writes that same state under the **new** symbol when props change. When both symbols already have chart data, the chart component is reused rather than remounted.

**Reproduced:** EURUSD had `[1.10]`, GBPUSD had `[1.30]`. Render EURUSD, then change the same chart component to GBPUSD. GBPUSD storage becomes **`[1.10]`**.

**Recommendation:** key the symbol-local drawing state/component by symbol, or use a per-symbol state map. If using a load effect, prevent the save effect from writing old state to a new key during the transition. Include account scope if drawings are private to an account.

**Required test:** A→B→A with both histories cached and distinct saved drawing sets; no write to B with A's data.

### R9 · P1 — Production WS token acquisition rejects legitimate browser GETs

**Evidence:** `server.ts:386–421,424–442`; `src/hooks/useWatchlistFeed.ts:182–225`.

The browser calls `fetch('/api/ws/token')`, a same-origin GET. With no shared secret in production, the endpoint requires `Origin`. The comment says browsers always send it here; that is incorrect. Normal same-origin GET/HEAD requests omit this header. [3](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/Origin)

**Reproduced against the real route:** no-Origin request → **403**; adding an allowlisted Origin with a non-browser client → **200**. The latter also demonstrates why Origin is not user authentication. I did not claim a real-browser end-to-end run; browser behavior here is checked against MDN/spec behavior plus the route reproduction.

Setting `WS_SHARED_SECRET` is not a complete fix for this browser client: it never sends the secret. Shipping that server secret in frontend code would defeat its purpose. After a token failure, the client still attempts an unauthenticated WS. On Node, upgrade can succeed before the connection handler closes it, so `onopen` can briefly mark it live and reset retry backoff.

**Recommendation:** decide whether market access is intentionally public or authenticated. For protected access, issue short-lived tokens from an authenticated, browser-compatible endpoint (for example a POST with origin checks plus a verified session), validate before upgrade, and mark streaming usable only after application-level acceptance. Keep Origin checks as browser-origin defense, not identity. Fall back to polling without retrying an impossible auth configuration forever.

Also correct the documentation: the saved token IP is not compared in the connection handler, and `?secret=` is still accepted. IP binding is a separate topology/mobile-client tradeoff, not a substitute for authentication.

**Required test:** production-origin browser flow, unconfigured auth, forged allowed Origin without a session, expired/reused token, multi-instance token handling, and sustained auth rejection with bounded retries.

### R10 · P1 when publicly enabled — Paid upstreams lack an account/global spending boundary

**Evidence:** `server.ts:498–522,654–681,764–794,856–886`; `server/lib/rateLimit.ts:70–108,116–165`.

`/api/chat` accepts unauthenticated requests that consume the server's configured AI account. The per-IP limiter is useful, but there is no account entitlement, daily cost budget, global concurrency budget, or code-level global spend ceiling. Supabase login in the UI does not protect this API. Missing ACAO for a disallowed origin prevents some browser reads; it does not stop a script/server from making the paid request.

**Reproduced:** an anonymous POST without Origin reached a **mocked** OpenRouter provider and returned 200. No real paid provider was called.

Cache protection is also incomplete: five concurrent identical `/api/market/quote` requests made **five** upstream fixture calls before any response populated the cache. A cache hit policy is not in-flight request deduplication, and process-local caches do not deduplicate across instances.

**Recommendation:** verify authentication server-side for paid features, or explicitly fund/cap a guest tier. Add shared per-account/global budgets where deployment requires them, provider billing limits/alerts, concurrent-request limits, input/output token budgets, and per-key in-flight deduplication. Fail closed or sharply reduce paid traffic when the distributed budget cannot be checked, rather than applying one universal fail-open policy to both cheap public quotes and billable AI. OWASP explicitly recommends spending limits for third-party integrations. [2](https://owasp.org/API-Security/editions/2023/en/0xa4-unrestricted-resource-consumption/)

**Required test:** anonymous/authorized requests, maximum cost/input/output, concurrent cache misses, multi-instance accounting, cancelled generation, and budget-store outage. If this is intentionally a private single-user deployment, downgrade urgency but keep provider-side budget protection.

### R11 · P2 — Timeouts stop at headers, and AI deadlines do not cancel work

**Evidence:** `server/lib/fetch.ts:40–87`; `server.ts:764–784`; `src/components/AiAssistant.tsx:116–139`.

`fetchWithTimeout` clears its timer as soon as `fetch` resolves to a Response. JSON/text consumption occurs later, outside the timeout. It also replaces rather than combines an incoming abort signal. `fetchJsonWithTimeout` does not repair the body deadline because it uses the same helper.

**Reproduced:** a local server flushed headers immediately and delayed the JSON body. A **50 ms** timeout completed successfully in approximately **194 ms**.

`Promise.race` in chat stops waiting but does not abort the losing provider operation. Its deadline timer also remains scheduled after success. Client cancellation isn't propagated to the provider. This weakens both resource control and the stated timeout guarantee.

**Recommendation:** bound connection, body consumption and maximum body bytes in the same abortable operation; compose caller/deadline signals; use SDK cancellation/timeout options; clear timers in `finally`; cancel downstream work on disconnect where supported. Keep structured upstream error categories.

**Required test:** immediate headers/stalled body, slow chunks, oversized body, already-aborted caller, client disconnect, timeout and fast-success cleanup.

### R12 · P2 — Vercel's quote path ignores the configured provider; platform assumptions are stale

**Evidence:** `server.ts:306–368,575–605`; `server/services/market.ts:208–230`; `api/index.ts:1–19`; `vercel.json`.

Persistent feed work is skipped under `VERCEL`. The HTTP price route calls **`fetchYahooPricesFor` directly**, even when Twelve Data is configured, while `marketSource()` reports `twelvedata` just because its key exists.

**Reproduced:** with a fixture Twelve Data key and `VERCEL=1`, one price request made eight Yahoo requests, returned zero prices after eight 503s, and still reported `success:true, source:'twelvedata'`.

More broadly, a configured primary provider is not necessarily the provider of each quote. Silver can be Twelve Data spot or Yahoo `SI=F` futures; those are not interchangeable instruments merely because both are displayed under `XAGUSD`. Quote/history responses need actual source/instrument metadata, not only one global label.

**Research correction:** the repository says Vercel Functions cannot serve WebSockets. That blanket claim is out of date. Current official documentation lists WebSockets in Beta, with instance pinning, maximum-duration disconnects, and external storage for durable/shared state. [3](https://vercel.com/docs/projects) See also the [official WebSocket guide](https://vercel.com/docs/functions/websockets) and [announcement](https://vercel.com/changelog/websocket-support-is-now-in-public-beta).

This does **not** mean the present deployment supports streaming automatically: its handler exports the Express app path, its browser connects at the root, and its persistent stream startup is explicitly disabled under `VERCEL`.

**Recommendation:** first make the current polling mode correct using the same provider-selection contract as Node. Return explicit transport capabilities so the browser need not repeatedly probe an unsupported path. Evaluate the Vercel WS beta separately; do not remove a guard and assume routing, distributed tokens, fan-out, and feed ownership are solved.

**Required test:** identical API contracts in Node and Vercel modes; configured/unconfigured/partial-provider fallback; actual source per instrument; and a deployed transport smoke test if adding WS support.

### R13 · P2 — Heuristic scores are presented as probabilities, and historical scores can repaint

**Evidence:** `src/utils/forexData.ts:361–371,467–554,716–728`; `src/components/PatternPanel.tsx:20–26,74–85,175–179,231`; `src/components/SignalPanel.tsx:218–219`.

Pattern “win rates” start from manually assigned values such as 64/68/71 and receive fixed indicator bonuses. Signal “confidence” is another deterministic score mapping. Neither is an empirically measured probability, and several indicators are correlated views of the same price series.

The disclaimer is an improvement, but “High Probability,” “Est. Win Rate,” and exact confidence percentages still imply validation that does not exist in this repository. Removing the fabricated pattern profit factor did not validate the remaining percentages.

There is also actual look-ahead in historical pattern scoring: `avgVolume` is computed over the **entire** dataset, including candles after the pattern being scored.

**Reproduced:** the same bullish-engulfing pattern changed from `winRate:69, volumeConfirm:true, score:72` to `winRate:64, volumeConfirm:false, score:64` solely after appending later high-volume candles. Its original candles were unchanged.

**Recommendation:** call these **heuristic confluence scores**, not win probabilities, until measured. Use causal trailing windows and distinguish provisional/forming candles from closed candles. If adding evaluation, define entry/exit rules, horizon, costs, data eligibility, out-of-sample splits, sample sizes and uncertainty. Do not optimize the score against the same historical sample used to report performance.

**Required test:** prefix invariance—appending future bars must not change a past closed-bar score—and consistent indicator conventions against reference fixtures. Validate strategy performance separately from software correctness.

### R14 · P2 / before the next public deployment — Runtime and CI health contracts are inconsistent

**Evidence:** `Dockerfile:2,19,45–49`; `.github/workflows/ci.yml:21–24,49–64,98–106`; `README.md:57–60`; `server.ts:372–383`.

- Docker and CI select **Node 20**, which is now EOL according to the [official Node.js release table](https://nodejs.org/en/about/previous-releases). README still recommends Node 18+, while installed `@google/genai` and Supabase client packages declare Node >=20.
- The production smoke loop waits only for HTTP 200, then immediately requires `status:ok`. Market sync runs asynchronously. The app can be alive and serving correctly before any external quote arrives.
- Docker/its CI smoke accepts that same 200 even when the feed is degraded. There is no shared definition of liveness versus feed readiness.

**Reproduced:** the built server booted, served the SPA and gzipped assets, and answered a JSON API 404 with the upstream intentionally unavailable. Health was `200/degraded`; the build-job grep would reject it, whereas the Docker check would accept it.

**Recommendation:** standardize a supported LTS runtime (Node 24 is a reasonable target; test the migration), pin it consistently, and separate process liveness, feature readiness and provider freshness. Stub upstreams in deterministic build smoke tests. Run live-provider canaries separately. Do not make a temporary external feed outage trigger an endless container restart loop.

## 6. Recommended implementation sequence

### A. Immediate containment and truthful UI

- Do not advertise mixed-currency totals as USD. Until R1 is fixed, show separated quote-currency results or disable the combined dollar metrics.
- Distinguish **stream connected**, **quote fresh**, **market closed**, **reference only**, and **feed unavailable**. Disable or explicitly label non-executable-price simulation.
- Relabel unvalidated win-rate/confidence displays as heuristic scores.
- Warn or temporarily gate cloud pull/account switching until data-loss/isolation paths are repaired. Preserve user exports before a migration.
- Put provider-side spending caps on any public AI deployment; stop using an EOL production runtime.

### B. Small, independently reviewable changes

| Order | Change set | Exit criteria |
|---|---|---|
| 1 | Shared instrument/quote/money contracts and versioned ledger | Mixed-currency book has correct units; realized results retain conversion provenance; unknown conversions cannot become dollar values |
| 2 | Atomic/idempotent order lifecycle; lossless execution events | Touch/rebound/gap/duplicate-event tests pass; render throttling cannot affect execution |
| 3 | History query lifecycle, bar rollover, chart data/indicator updates | StrictMode and rapid-switch tests pass; no timestamp corruption; overlays match the same revision; markers do not accumulate |
| 4 | Per-account persistence and safe sync protocol | Two-account, in-flight-edit, close/restore and retry tests pass against a scratch Supabase project, including RLS and migration/rollback checks |
| 5 | Feed health/provider parity, browser token flow, bounded upstream operations | Correct Node/Vercel provider provenance; stale/missing/429/body-stall fixtures; authenticated browser flow and graceful fallback |
| 6 | Paid API budgets and operational tests | Server-side auth/guest cap, provider limits, in-flight dedupe, concurrency/cancellation tests, supported runtime and deterministic CI |
| 7 | Measured performance, mobile/a11y, docs reconciliation | Smaller logo, deferred nonessential panes, profiler/browser results, keyboard smoke, and one current status document linked to tests |

Some containment/runtime changes are small. The ledger/sync changes require migration and recovery decisions; treating this whole review as a “four-hour cleanup” would be unrealistic. Prefer staged fixes with clear acceptance tests over one large rewrite.

### C. Tests to add before claiming production readiness

Keep the existing utility tests. Add the missing layers:

- **Domain tests:** denomination/conversion, order idempotency, price eligibility, event ordering, and causal indicators.
- **React integration tests:** StrictMode history, transport cancellation, drawing/account switches, in-flight sync edits, and chat reset while a response is pending.
- **API integration tests:** real middleware and routes with fake providers, auth/quotas, timeouts through body consumption, JSON errors, partial outages and single-flight caching.
- **Database tests:** schema migration on old/new databases, RLS for two users, close/restore atomicity, tombstones/version conflicts and pagination completeness.
- **Browser smoke tests:** production build, same-origin auth/WS, forced polling, symbol/timeframe navigation, chart snapshots, order/close/restore, mobile tabs and keyboard use.
- **Separate deployment canaries:** current paid model IDs, data-provider entitlements and real platform routing. Do not make every pull request depend on live financial-data uptime.

The important invariants are: **money retains its currency; a closed position cannot reopen from an old snapshot; one user's local records never become another's implicitly; every displayed quote/bar has identity and time; rendering optimizations cannot change execution outcomes.**

## 7. Critique of the repository and the previous reviews

### The product's presentation is ahead of its verified correctness

There is considerable UI and feature work here, but labels such as “professional,” “live,” “high probability,” and dollar P&L currently promise stronger semantics than the state model supports. Real upstream data does not automatically mean a current executable quote, the same instrument across fallbacks, or a validated prediction.

This is fixable. The response should be less ambiguous data and narrower claims—not another layer of branding, another indicator, or a disclaimer placed far from the affected number.

### The tests are valuable, but many prove the wrong boundary

A test that `computePnl` correctly returns 100,000 JPY does not prove a dollar dashboard is correct. A test that `mergeById` preserves its arguments does not prove a React handler uses current state after `await`. A tested trailing throttle does not prove it preserves barrier crossings.

Several previous fixes improved a local function while leaving its consumer contract implicit. The new tests should start from user-visible invariants and expected units, then work downward.

### Optimizations must preserve meaning

The two clearest examples are coalescing execution ticks and updating only the candle series. Both reduce work; both change the meaning of the output. Keep presentation sampling separate from the ordered domain events, and make every chart overlay share the same data revision.

### Security concepts have been conflated

Origin checks are not user authentication. CORS headers are not a server-to-server access boundary. RLS is not local-storage account isolation. Rate limiting by IP is not a spending budget. A timeout on receipt of headers is not a deadline on an entire request.

The repository does contain useful defenses. The critique is of what those defenses are claimed to guarantee, not an assertion that the app has no security.

### Previous “fixed” claims cannot be used as current release evidence

The historical documents describe different branches and sometimes explicitly acknowledge deferred work. They should remain historical rather than be read as current guarantees. Examples of current discrepancies:

| Existing claim | Current checkout |
|---|---|
| `CHANGES.md`: WS tokens are IP-bound and `?secret=` removed | IP is stored but not compared; query secret remains (`server.ts:398,419,434–442`) |
| `CHANGES.md`: one Yahoo v7 batch quote request | `server/services/market.ts:144–152` fans out one chart request per instrument |
| `CHANGES.md`: side-effect-free server import, matching teardown | HTTP/WS objects and token/limiter timers are created at module scope; non-Vercel imports start feed/server work; no claimed teardown function |
| `CHANGES.md`: CSV escaping, API Cache-Control and request-ID correlation added | CSV uses raw joins; those middleware guarantees are not implemented as claimed |
| `FIXES_APPLIED.md`: refusing absent Origin costs nothing legitimate | Contradicted by the actual browser request shape and R9 |
| `FIXES_APPLIED.md`: additive merge prevents local data loss | The pure helper does; the awaiting component handler still loses in-flight changes (R6) |
| `FIXES_APPLIED.md`: final-tick throttling preserves execution | It preserves the latest value, not all stop/target touches (R2) |
| `api/index.ts` and deployment narrative: Vercel cannot host WS | Outdated platform claim; the current app remains polling-only by its own implementation (R12) |

Do not interpret this table as an attribution of intent or proof of which change introduced a regression. It is a comparison against the reviewed commit. In particular, the old `DEEP_REVIEW.md` “A−” verdict is not a current readiness assessment.

**Process recommendation:** archive overlapping review/fix logs as historical, keep one current risk register, and link each resolved item to a regression test and commit. A list of green compiler/linter commands cannot establish that a particular workflow is fixed. Also avoid absolute claims such as “secrets cannot reach logs” or “IDs cannot collide” where the evidence is a limited pattern test or random-ID sample.

## 8. Critique of these recommendations: avoid overcorrecting

1. **Do not introduce microservices/Kafka/a new web framework to fix state ownership.** A modular monolith, explicit domain types, a reducer, and a small query cache can solve most of this. Shared infrastructure is justified when deployment topology or global budgets require it.
2. **Do not wire the unused indicator cache in as a quick performance patch.** Its invalidation contract is incomplete. First establish correct revisions; then profile and cache.
3. **Do not “fix” account mixing by deleting all local data on every login.** That prevents one leak by creating another data-loss path. Partition books and offer a deliberate guest import/migration.
4. **Do not treat timestamps alone as complete execution fidelity.** Polling and browser suspension miss market events. Either describe the simulator as observed-quote/local-only, or design a durable server-side execution service if that fidelity is a real requirement.
5. **Do not move to Vercel's WS beta merely because it is now available.** Its duration and distributed-state constraints still apply; fix the supported polling path first unless streaming there is a product requirement.
6. **Do not mistake a backtest for proof of future profitability.** Software correctness, causal evaluation, and strategy usefulness are separate questions. Accurate labeling is possible now, without inventing a new “confidence” number.
7. **Do not blindly run `npm audit fix --force`.** The observed findings are moderate and include development tooling; the simple parser is a meaningful mitigation for query parsing. Review supported patched versions, separate runtime/dev exposure, and retest changes. A major upgrade is not a substitute for fixing the proven data-loss defects.
8. **Do not call the next pass complete using only this review's fixture results.** Supabase migrations, real-browser behavior, actual Vercel routing, market entitlements and paid model availability need validation in the target environment. This report cannot establish those without exercising them.
