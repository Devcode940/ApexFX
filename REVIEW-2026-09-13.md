## 1. Verdict

**Grade: C+ (was B+ in `REVIEW.md`). Downgraded from the previous review.**

The product is genuinely impressive: a real, multi-source market terminal with a clean charting module and a "real data only" policy that the code actually respects. The engineering *taste* is above average for a solo project.

What changed my grade is the **gap between documentation and reality**. `FIXES_APPLIED.md` claims 16 of 16 issues fixed and lists a verification section ("tsc passes, 13 tests pass, build succeeds"). That is technically true and materially misleading: the two quality gates it claims to have added (**ESLint** and **strict types**) are non-functional, the security fix it claims (**log redaction**) leaks keys on the exact code path that matters, and the AI feature it documents is pointed at a **model Google shut down on 2026-06-01**. A green CI that runs a linter which crashes and then `|| echo`s the failure is worse than no CI, because it manufactures false confidence.

This is not a "lots of bugs" project — it is a "good project whose safety nets are placebo" project. Both are fixable in about two days.

## 3. What is genuinely good

Fair credit, because it's real and it constrains how you should refactor:

- **`useChartCore.ts` + `utils/chart/` + `components/chart/`** is the best code in the repo. Ref-mirrored props (`activeToolRef`, `drawingsRef`) to keep a stable chart lifecycle, dedicated effects for `data` vs. markers vs. price lines instead of teardown/recreate — that is the correct fix for the "chart recreates on every tick" problem, and it was clearly understood, not cargo-culted.
- **Indicator math is correct.** Wilder smoothing on RSI/ATR, proper EMA seeding, Bollinger population stddev, and the volatility baseline that **excludes the latest candle to avoid self-dampening** — with a regression test asserting exactly that. The test suite is small but the tests that exist are *meaningful* (they assert behavior that could plausibly regress, not `expect(x).toBeDefined()`).
- **`watchlistRef` in `useWatchlistFeed`** to defeat stale closures in WS/poll callbacks: correct and idiomatic.
- **Per-symbol degradation**: Twelve Data → Yahoo fallback per symbol (`applied` set + `remaining`), 429 cooldown, `query1`→`query2` retry. This is how you're supposed to build against flaky upstreams.
- **Honest data policy.** No synthetic ticks anywhere; `price: 0` rather than fabricated numbers; graceful `Live market data unavailable` handling. For a trading app, this integrity is worth more than most features.
- **Supabase is opt-in with no placeholder client**, and RLS is `auth.uid()`-scoped on every table including a `handle_new_user` trigger.
- Graceful `if (!process.env.VERCEL)` guard around timers — right idea, wrong execution (see §4.8).

## 4. Findings

Severity: **S1** = ship-blocker / broken or leaking today · **S2** = high, will bite users or the bill · **S3** = medium, quality/robustness · **S4** = nit.

### S1.1 — The AI assistant is dead on arrival for every Gemini user
`server.ts:633` calls `model: 'gemini-2.0-flash'`. Google's release notes: *"June 1, 2026 — the following Gemini 2.0 models are now shut down: gemini-2.0-flash, gemini-2.0-flash-001, gemini-2.0-flash-lite, gemini-2.0-flash-lite-001. Use gemini-3.5-flash or gemini-3.1-flash-lite instead."* Every request 404s. Because `OPENROUTER_API_KEY` is optional and the README's first-class path is Gemini, the flagship feature ("real AI, no canned fallbacks") fails for the default configuration — and the failure is a generic `500 { error: 'An error occurred while processing your request.' }`, so nobody can tell it's a model-name problem. README §3 claims `gemini-3.5-flash`: **the doc was updated, the code wasn't.**

Fix: `const GEMINI_MODEL = process.env.GEMINI_MODEL || 'gemini-3.5-flash';` — and on `404`/`400`, return the upstream body (`Failed to fetch from Twelve Data`-style stringification already exists for OpenRouter at `server.ts:~395`). Do not hardcode model IDs; that is precisely the failure mode the retirement cadence punishes.

### S1.2 — Secrets: `.env` is not ignored, and a live Firebase key is already committed
`.gitignore` contains `.env.local` but **not `.env`** (verified: `git check-ignore .env` → unmatched; only `.gitignore:3:.env.local` matched). README §"Environment Setup" instructs users to create **`.env` at the repo root** with `GEMINI_API_KEY`, `TWELVEDATA_API_KEY`, `FINNHUB_API_KEY`, `WS_SHARED_SECRET`, `UPSTASH_REDIS_REST_TOKEN`. `git add .` ⇒ all of them in history. This is the highest-probability credential leak in the project — one careless commit by the next contributor.

Separately, `firebase-applet-config.json` is **tracked** and contains a live key: `apiKey: AIzaSyA1NPi3WA6LF8CioIm6wRWn7nhBW89Um8k`, project `abiding-operand-465801-a1`, plus a Firestore DB id. Nothing in `src/` imports Firebase (grep: zero hits for `firebase`/`VITE_FIREBASE`) — so this file's only function is exposure. `firestore.rules` and `firebase-blueprint.json` are equally orphaned; the app uses Supabase.

Fix: add `.env`, `.env.*`, `!.env.example` to `.gitignore`; rotate that Firebase key and delete the three files (or move them to a `docs/legacy/` with the key scrubbed). Add a `gitleaks`/secretlint step to CI.

### S1.3 — "Redacted" logging leaks API keys into production logs (PoC)
`server/lib/logger.ts` sanitizes **only `msg`**, never `...args`. `fetchWithTimeout` builds its timeout error as `` `Request timed out after ${timeoutMs}ms for ${url}` `` — and after commit `6ce497e` ("restore query-param auth"), that URL **contains** `apikey=` / `token=` / `api_key=`. Every call site passes the message as a second arg:

```
server/services/market.ts:112   error('[TwelveData] quote fetch failed:', (e as Error).message)
server/services/yahoo.ts:60     warn('[TwelveData] time_series fetch failed:', (e as Error).message)
server/services/market.ts:157   error(`Failed to fetch real price for ${item.symbol}:`, e)   // full Error + stack
```

Verified PoC against a hanging upstream, using a byte-exact copy of `logger.error`:

```
### CASE 1 (what market.ts does):
[TwelveData] quote fetch failed: Request timed out after 300ms for http://…&apikey=TD_SECRET_abcdef123456   ← LEAK
### CASE 2 (secret inside the first arg, same sanitizer):
[TwelveData] fetch failed Request timed out after … &api_key=[REDACTED]                                     ← redacted
```

Note `error()` is *not* gated on `SHOW_WARNINGS`, so this prints in production, into whatever log drain you have (and `logError('Failed to fetch historical data:', e)` in `server.ts` does it with the whole Error object, stack included). Also `console.warn` in `safeSend` bypasses the sanitizer entirely.

Fix (30 min, do all three): (1) sanitize every arg, not just `msg`; (2) stop putting keys in URLs — send `Authorization: Bearer` or a header for Twelve Data/Finnhub/ForexRate where supported, or centralize a `redactUrl()` applied in `fetchWithTimeout` before it interpolates the URL into an error; (3) never embed `url` in thrown messages.

### S1.4 — Rate limiting bypassable with one header; `/api/health` unlimited
`sanitizeClientIp` returns the **first** `x-forwarded-for` value with zero validation and no `app.set('trust proxy', …)` anywhere (grep: none). Behind *any* proxy — i.e. every real deployment — a client can send a fresh XFF per request and get an **unbounded** budget. Measured: 35/35 `200`.

The blast radius is not "somebody scrapes prices". It is: `/api/market/quote` and `/api/market/history` are **uncached passthroughs that spend the operator's paid/quota'd Twelve Data credits** (README: 1 credit per symbol). Unbounded XFF + `setInterval(fetchQuote, 60000)` per tab means one attacker (or 50 users) drains the 800/day free allocation or bills a paid plan. `isRateLimitedSync` on token issuance has the same flaw.

Compounding: `app.use('/api', rateLimitMiddleware)` sits **below** the `/api/health` and `/api/ws/token` route definitions in `server.ts`, so those two never hit the limiter (measured: 40 × `/api/health` → all 200). `/api/health` discloses `uptime`, `wsClients`, `watchlist` size, and `NODE_ENV` — a free recon endpoint, unthrottled, forever.

Fix: register `app.disable('x-powered-by')` + the limiter **before any route**; gate XFF behind `app.set('trust proxy', 1)` (or `UPSTREAM_PROXY` env) and fall back to `req.socket.remoteAddress`; cache `/api/market/quote` in `priceCache` (10–15 s) since the server already holds `serverWatchlist`; move `/api/health` to `/healthz` outside `/api`.

### S1.5 — Production build ships a broken logo, and the SPA fallback hides it
`src/App.tsx:15`: `const appLogo = '/src/assets/images/app_logo_1782444134483.jpg';` — a raw path, not an `import`. Vite only fingerprints *imported* assets, so `dist/` contains no image (`find dist -name '*.jpg'` → empty). The prod catch-all then serves **`index.html` with HTTP 200** for that `.jpg` URL, so the browser renders a broken `<img>` and there's no 404 to find in devtools or CI. In dev it works — which is exactly why it was never noticed.

Fix: `import appLogo from './assets/images/app_logo_1782444134483.jpg';` (add `declare module '*.jpg'` if needed — `vite/client` types already cover it). Then make the prod fallback 404 on any path containing a file extension so this class of bug self-reports.

### S2.1 — Silver (`XAG/USD`) history is broken by an internal contradiction
`server/services/market.ts:120` maps `'XAGUSD' → 'SI=F'`, and README §1 states the reason: *"Silver is served from COMEX silver futures (SI=F) … because … Yahoo has no silver spot feed."* But `server/services/yahoo.ts:71` maps `'XAGUSD' → 'XAGUSD=X'`. The codebase documents that its own history ticker does not exist.

Consequence: without a Twelve Data key (the README's advertised zero-config path), **every chart except silver works** — silver returns 404 → `fetchYahooHistory` throws → `/api/market/history` 500 → `useChartHistory` writes `[]` and never retries, so the user sees an empty pane with no error. Same asymmetry means price and chart for silver are priced off two different instruments (`SI=F` futures vs. spot), so **paper-trade P&L and SL/TP triggers for silver are computed against one series while the chart draws another** — in a trading app, an entry price the chart never showed is a real bug, not a nit.

Fix: one shared `YAHOO_SYMBOLS` map exported from `market.ts` and imported by `yahoo.ts`; make the chart use the same `SI=F`. Add a unit test asserting the two maps agree for all 8 instruments (this bug is *only* preventable by a test, since it's a duplication bug, not a type error).

### S2.2 — 429s are invisible, and the client is 5 requests from its own limit
An idle single tab in fallback-polling mode issues `/api/market/prices` every 2.5 s (24/min) + `/api/market/quote` every 60 s (1/min) ≈ **25 of the 30 req/min budget**. Add a second tab, a second device, or a couple of timeframe switches and you exceed it permanently. Then:
- `startPolling()`'s catch is `catch { /* Silent catch to prevent console spam */ }` — 429s are swallowed. The user sees **frozen prices with no indication**, while `wsConnected=false` is displayed only as a small badge.
- `isRateLimited` has no `Retry-After`, and the client has no backoff-on-429 path, so the client keeps hammering at 2.5 s while rate-limited — self-sustaining congestion.
- On WS failure the client retries `connect()` every 5 s, and each attempt re-requests `/api/ws/token`, which has its own **10/min** limit → after two minutes you are generating a 429 storm on your own auth endpoint.

Fix: exponential backoff with jitter on 429/`network error`; surface a `feedDegraded` state in the HUD; send `Retry-After` and key the limiter per-endpoint-class with a real budget (prices 20/min, quote 10/min, chat 10/min, health exempt); pause polling on `document.hidden`.

### S2.3 — No backoff on upstream failure ⇒ log flooding, and the only visible symptom
Reproduced locally (sandbox has no egress): with Yahoo unreachable, the server printed **8 full stack traces every 5 s** — `Failed to fetch real price for EURUSD: TypeError: fetch failed` ×8 instruments, forever, in `NODE_ENV=production`. Two problems: (a) no circuit breaker/backoff on total upstream failure, so a 30-minute Yahoo outage = 28,800 log lines and 14,400 failed request cycles; (b) `log()` is a **hard no-op in production** (`IS_PRODUCTION ? noop : console.log`), so there is no `info`-level signal at all — you cannot distinguish "degraded" from "healthy" in prod logs, only a wall of `error`.

Fix: consecutive-failure counter → back off 5 s → 15 → 30 → 60 s max, one log line per state change (not per failure); keep `log()` but route through a level filter (`LOG_LEVEL`) instead of nulling it in prod.

### S2.4 — `strict` off hid 25 type errors, including a live crash path
`npx tsc --noEmit --strict` → 25 errors. Not cosmetic:
- `PositionsPanel.tsx:95,158,159,192,193,288,318,328` — `'activeSignal' is possibly 'null'` ×8. Context types it `TradingSignal | null`. It survives today only because `generateSignal` happens to always return an object (its `data.length === 0` branch returns a placeholder). One refactor to `return null` on empty data and the **entire trader panel throws** — with only the root `ErrorBoundary` to catch it, i.e. a blank terminal.
- `SupabaseSync.tsx` ×9 — `'supabase' is possibly 'null'`. Guarded by `isSupabaseConfigured` checks that TS can't see. This is the component that talks to the database; every one of those 9 needs a real narrowing guard.
- `server.ts:618-619` — `'ai' is possibly 'null'` **plus** `server.ts:634` `Type '({role;parts}|null)[]' is not assignable to 'ContentListUnion'`: the `.filter(c => c && …)` result is typed `(T|null)[]`, so the null-stripping isn't visible to the compiler. Here the runtime guard exists; the type doesn't.

Fix: turn on `strict` **per-directory** (allow-list `src/utils/**`, `server/**` first), or set `"strict": true` with `noImplicitAny: false` for one release. Then fix the 25. The 17 null-dereferences are the actual bug class; do those first.

### S2.5 — The ESLint gate that would have caught the React bugs doesn't run

### S2.6 — Vercel deployment story is decorative, and one config is dead code
- `vercel.json` uses **legacy `builds` + `routes`**. When `builds` is present, Vercel ignores filesystem function detection ⇒ **`api/index.ts` is never built**. `FIXES_APPLIED.md`/README document it as "Vercel serverless entry" — it is dead.
- Even if it were built: `export default app` (an Express instance) is not a valid Vercel Node handler (needs `export default (req,res)`); it would only work via `@vercel/node`'s express detection on the `builds` path that excludes it. Two mutually-exclusive mechanisms are configured and neither is correct.
- `CHAT_TIMEOUT_MS = 45_000`, but `vercel.json` sets **no `functions.maxDuration`** ⇒ default 10 s (5 s on some Hobby configs). AI chat **cannot** complete on Vercel; it 504s after 10 s while the client waits 50 s. The README's "no canned fallbacks; surfaces the real error" will surface a timeout nobody can interpret.
- All server-side state (`wsAuthTokens`, rate-limit buckets, `serverWatchlist`, both LRU caches) is per-instance in-memory — acknowledged in the old review, still true. On Vercel `/api/market/prices` is served from a `serverWatchlist` populated only inside `if (process.env.VERCEL && …)` at request time; `fetchYahooPricesFor` fires **8 upstream calls per cold-started request**, uncached across instances, inside a 10 s budget — likely to time out under any concurrency.
- The Upstash limiter **fails open** on error, uses two sequential round-trips (`INCR` then `EXPIRE`), and if the process dies between them the key never expires ⇒ that IP is **permanently blocked**. Use `GT`/pipeline or Upstash's `/pipeline`, and set expiry atomically.

Recommendation: declare Vercel unsupported for the WS/full mode (README half-says this already), keep `vercel.json` minimal, and set `"functions": {"server.ts": {"maxDuration": 60}}` if you keep it.

### S2.7 — Metric integrity: "Profit Factor" is not a profit factor
```js
winRate      = clamp(baseWinRate, 38, 89)                      // heuristic, fine
reliability  = winRate > 75 ? 'High' : winRate >= 64 ? 'Medium' : 'Low'
profitFactor = 1.1 + (winRate - 45) * 0.025                     // ← derived from the same number
score        = winRate * (volumeConfirm ? 1.05 : 1) * (reliability === 'High' ? 1.1 : 1)
```
`profitFactor` is a **linear transform of `winRate`** (`forexData.ts:556`) displayed as "Profit Factor" — a term traders define as gross profit ÷ gross loss. It is not an estimate of that; it is a monotone relabeling. Same for `score` (a 1.05/1.1 multiplier on a heuristic) feeding `SignalPanel` confidence. The disclaimers ("heuristic estimates, not backtested") are well written and I'd keep them, but a disclaimer doesn't make a tautology a metric — `profitFactor` will move in lockstep with `winRate` and a user comparing the two will draw a false conclusion.

Fix: rename to `Pattern Strength Index` / drop `profitFactor` entirely, or compute a genuine one by replaying the detected pattern against `activeData` (you already have the candles; a 20-line forward-return walk gives a *real*, if small-sample, figure). Given the "real data only" brand, this is the one place the project's own standard argues against it.

### S3.1 — `setClosedTrades` inside the `setPositions` updater ⇒ duplicate trades
`usePaperTrading.ts` `handleClosePosition`:
```js
setPositions((prev) => { …; setClosedTrades(prevClosed => [trade, ...prevClosed]); return prev.filter(…) })
```
Updater functions must be pure; React 19 + `<StrictMode>` (enabled in `main.tsx`) **double-invokes them in dev** ⇒ each manual close writes **two** rows to `closedTrades`, and both are pushed to Supabase/CSV, corrupting win-rate and profit stats in exactly the dev environment where you'd debug it. `Math.random()` inside the updater also makes `id` unstable across the double call, so React can't dedupe it even by key.

Fix: compute the target from `positions` (already in scope) outside the updater, call both setters as separate top-level statements. Add a test: `closePosition` twice ⇒ `closedTrades.length === 1`.

### S3.2 — Positions can open at price 0 with no guard
`handleOpenPosition` uses `currentPrice` directly; `currentPrice` is `0` until the feed fills (server `serverWatchlist` starts at `price: 0`, and `useChartHistory` may also be empty). `handleOpenMarketOrder` validates `amount > 0` and SL/TP ordering vs. `currentPrice`, but never `currentPrice > 0`. With `currentPrice === 0`: BUY with `sl/tp` → `slValue >= 0` → "Buy Stop Loss must be under market price" (misleading message); BUY without SL/TP → **a position with `entryPrice: 0`** is created, and P&L becomes `livePrice × amount × contractSize` — e.g. 1 lot EURUSD at 1.085 ⇒ **+$108,500 phantom profit** shown and written to history. The `usePaperTrading` PnL effect skips `priceItem.price === 0` but that guard doesn't prevent opening at 0.

Fix: `if (!(currentPrice > 0)) { setErrorText('Waiting for live price…'); return; }` and hard-disable the BUY/SELL buttons when `currentPrice === 0`.

### S3.3 — Supabase sync: client-generated PKs collide across users; `pips` wrong for metals
`positions.id` / `closed_trades.id` are `pos_<Date.now()>_<4 chars>` (`Math.random().toString(36).substr(2,4)`) with `id TEXT PRIMARY KEY` **shared globally**, upserted `onConflict: 'id'`. Two authenticated users trading within the same millisecond bucket collide on a 36^4≈1.7M space; because RLS does not hide unique violations, the second user gets `duplicate key value violates unique constraint` — a confusing sync failure that also *discloses that an id exists*. Also `pips: 0` hardcoded on positions, and `pips: Math.abs(Math.round((exit-entry) * (symbol.includes('JPY') ? 100 : 10000)))` — which for `XAUUSD` (pip = 0.1, contract 100 oz) overstates by 100×.

Fix: `id uuid default gen_random_uuid()` (or namespace as `user_id || ':' || local_id`), store pips from `PAIRS_CONFIG[symbol].pipDecimal`, and derive pips from one shared helper used by both client and DB layers.

### S3.4 — React/feed correctness nits that compound
- `TradingContext` rewrites the **whole `chartData` object** on every tick to update one candle (`setChartData(prev => …)`), which `useChartCore`'s `[data]` effect then `setData`s — the claimed `chart.update()` optimization (§11 of FIXES_APPLIED) is only *partially* true: it avoids **recreation** (good) but still replaces arrays + full `setData` per tick, so cost is O(candles) per tick per open symbol/timeframe. With 800 candles × 8 symbols cached, that's measurable.
- `useChartHistory`'s effect depends on `chartData` and re-runs on every tick (guard `if (!chartData[sym]?.[tf])`) — cheap but avoidable; and on failure it stores `[]`, which permanently suppresses retry: **one transient 500 leaves the chart empty until the user switches symbol twice.** No `Retry`, no `AbortController`, no error surface.
- `liveQuote` polling calls `/api/market/quote`, which returns 500 without a Twelve Data key ⇒ that HUD element is **permanently null in the zero-config path** while consuming a request every 60 s.
- `AiAssistant.handleSendMessage` re-sends **every historical `image`** on each new message; server caps history at 30 msgs but keeps all base64 payloads ⇒ a few snapshots blow past `express.json({limit:'1mb'})` (→ raw 413, `res.json()` throws client-side → "Unknown error") and pay for the same image repeatedly on every subsequent turn.
- `handleTakeSnapshot` (see S1.5 context) also fires a `CustomEvent('apexfx:snapshot')` that **no component listens for** (grep: zero listeners) — dead channel from an earlier refactor.

### S3.5 — Performance: 1.33 MB single chunk, zero compression, O(ticks × clients) broadcast
- `vite build` warns and ships one 1,328 kB JS chunk (384 kB gzipped, **~1.3 MB over the wire uncompressed** because no `compression` middleware is installed). No `manualChunks`, no route/panel-level `React.lazy` — `recharts`, `lightweight-charts`, `motion`, and `@supabase/supabase-js` are all in the critical path for a page whose first paint is a chart.
- `broadcastPrices()` is called from **inside `tdWs.on('message')` per tick** and re-`JSON.stringify`s the entire 8-symbol payload for every price event, then sends to every client. In an active session Twelve Data streams many ticks/sec ⇒ stringify-per-tick-per-client. Coalesce: mark dirty, flush on a 100–250 ms `setTimeout`/interval.
- Google Fonts via `@import` in `index.css` = render-blocking extra round trip, with no `<link rel="preconnect">` in `index.html` (which also has no favicon, no `theme-color`, no `og:`/`description` meta for a product people will share).
- `index.html` sets no cache headers for hashed assets; `express.static(distPath)` runs without `maxAge: '1y', immutable` ⇒ revalidation churn on every nav.
- `/api/market/prices` double-caches (`priceCache` + `lastPriceFetchTs` doing the same 4 s job, in a way that makes the cache key redundant) and `/api/market/history` never invalidates on symbol change beyond TTL — fine, but the double-cache reads as a leftover.

### S3.6 — Accessibility: effectively unbuilt
- **99 `<button>` elements, 0 `aria-label`** across all components (measured). Icon-only controls (sidebar toggles, theme, snapshot, indicator chips, pagination) announce nothing.
- `index.css` has custom keyframes and `.tick-*-flash` transitions with **no `@media (prefers-reduced-motion: reduce)`** guard — flashing green/red price animations are a genuine vestibular/photosensitivity concern for a trading UI.
- No skip link, no visible `focus-visible` treatment, no keyboard handling for the chart toolbar or drawing tools; the mobile tab bar (`App.tsx`) is buttons without `role="tablist"`/`aria-selected`.
- `ErrorBoundary` renders `{this.state.error.message}` — raw internals for a user-facing failure, and the only recovery action is a full reload.
- `<img>` alts and `referrerPolicy="no-referrer"` are present (good) — the gaps are concentrated in interactive controls.

### S3.7 — Test suite: right tests, wrong scope
13 passing tests in **1 file covering 1 of 45 modules**, all pure functions. Coverage of the parts that actually break is **zero**: `server/lib/*` (rate limit, cache, security, logger), `server/services/*` (429 cooldown, per-symbol fallback, env validation), `useWatchlistFeed` (reconnect/polling state machine), `usePaperTrading` (SL/TP, dedupe), `SupabaseSync` mapping, and the `XAGUSD` map consistency bug in S2.1. Every S1/S2 finding in this review is in untested code. The three tests that exist for indicators are high quality (the RSI 100/50 boundary cases and the volatility self-dampening regression show real understanding) — the problem is entirely about where they're aimed.

Concrete, cheap high-value tests: (1) `sanitizeClientIp` must ignore XFF unless `trust proxy` is on; (2) `logger.error('msg', '…apikey=X')` must not contain `X`; (3) `YAHOO_SYMBOLS` in `market.ts` and `yahoo.ts` agree for all 8 symbols; (4) `getQuoteSyncMs()` clamping (10s/1h) and `Number('') || default` behavior; (5) `LRUCache` TTL expiry + eviction; (6) 429 → cooldown → recovery using a mocked `fetch`.

## 7. Bottom line

The domain work — indicators, pattern detection, dual-feed resilience, chart lifecycle management — is well above typical solo-project quality, and the "real data only" discipline is real. What the repo needs is not more features but **less optimism in its own safety nets**: a linter that cannot start, a type checker with strictness disabled, a log sanitizer that misses the one call site that matters, a CI that `|| echo`s past every failure, and a README describing an AI model that no longer exists. Each of those is cheap to fix; collectively they're the difference between a project I'd merge with P0s and one I'd hold.

If it were a PR: **request changes** — P0 items 1–6, plus a doc-accuracy pass, then I'd approve.
